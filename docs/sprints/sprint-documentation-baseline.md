# Sprint：项目知识基线

## 目标

从代码、资源、构建文件和 Git 历史还原项目的产品意图与技术结构，形成未来会话可以逐层读取、持续修订的项目文档基线。

## 硬锚点

- 文档采用逐层披露：根 README 回答“这是什么”，`docs/README.md` 回答“分成哪些部分”，产品与架构文档回答“各部分如何协作”，专题参考文档再下钻到文件、符号和行号。
- 每一层都必须能独立回答该层读者的问题，同时链接到下一层；不得要求新会话先遍历源码才能理解项目。
- 所有事实以代码、资源、构建文件或 Git 历史为证据；推断和未知项必须显式标注。
- `Rampage` 作为最后演化的代码线重点描述；其他三个顶层目录作为基线或历史谱系保留说明。仓库证据不能证明用户机器实际加载的是哪个模组。
- 文档必须说明仓库是覆盖包，不是完整、自包含的游戏发行物。
- DLL、XML Schema、XML 数据、Python 入口和资源定义是一组跨层契约，不能拆开描述成互不相关的模块。
- 项目没有关系数据库，不创建虚假的数据库设计文档。
- 产品、架构、接口和测试计划属于无状态设计契约；Sprint 与环境状态可以记录当前状态。
- 不修改 `human/`，不写入跨项目 memory，不提交或推送 Git。

## 模块

### M1：产品语义

- 描述：从可观察的规则、界面与数据定义还原目标用户、核心玩法、功能边界和交互面。
- 输出：`docs/product/*`
- 依赖：无
- 工时：M

### M2：技术架构

- 描述：说明代码谱系、运行时组件、跨层数据流、技术栈、约束矩阵与失败场景。
- 输出：`docs/architecture/*`
- 依赖：M1 可并行起草，收口时对齐
- 工时：M

### M3：接口契约

- 描述：把 XML 到 C++、C++ 到 Python、事件和 UI 入口等隐式接口整理为可查询的参考文档。
- 输出：`docs/api/*`
- 依赖：M1、M2
- 工时：M

### M4：环境与操作

- 描述：记录依赖环境、安装覆盖流程、旧工具链构建路径、调试假设、状态和排障方法。
- 输出：`docs/ops/*`
- 依赖：M2
- 工时：M

### M5：验证策略

- 描述：定义在 macOS 只读工作区可执行的静态检查，以及 Windows 游戏环境中的构建和运行验收层次。
- 输出：`docs/testing/*`
- 依赖：M2、M3、M4
- 工时：M

### M6：方法索引与入口导航

- 描述：登记跨多处使用或封装非平凡逻辑的方法，并让全部文档从根入口两次跳转内可达。
- 输出：`docs/common-methods.md`、`README.md`、`docs/README.md`
- 依赖：M1 至 M5
- 工时：M

### M7：统一审查

- 描述：核对事实证据、文档边界、相互链接、路径大小写、无状态约束和未知项。
- 输出：审查结论与必要修订
- 依赖：M1 至 M6
- 工时：M

## 执行顺序

1. M1 与 M2 并行建立词汇和边界。
2. M3、M4 基于前两层展开。
3. M5 基于接口与环境约束定义验证策略。
4. M6 汇总导航与方法索引。
5. M7 做跨文档审查并收口。

依赖关系为 DAG，不存在循环依赖。

## 完成标准

- 根 README 在一个短篇幅内说明项目定位、重点代码线、主要组成和推荐阅读顺序。
- `docs/README.md` 给出项目组成地图，并将每个部分链接到对应的深入文档。
- 新会话从根 README 能在两次跳转内找到产品、架构、接口、运维、测试和 Sprint 文档。
- 每个关键结论都能定位到仓库证据，或明确标注为推断/未知。
- 文档明确区分 `Rampage` 现行代码线与历史目录，避免后续修改错目标。
- 文档覆盖核心战斗、远程攻击、移动与容量、工人占格、玩家食物经济五类定制机制。
- 文档覆盖完整的 XML → C++ → Python/UI 数据与事件链路。
- 安装和构建文档不声称当前 macOS 环境可以运行 Windows 游戏或重建 DLL。
- 所有 Markdown 相对链接可解析，不存在孤立文档。
- `docs/common-methods.md` 符合“项目 → 类/对象 → 方法”的索引结构。
