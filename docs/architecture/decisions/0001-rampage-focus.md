# ADR-0001：以 Rampage 作为仓库理解重点，但不声明运行目标

- **状态：** 接受
- **日期：** 2026-07-15
- **范围：** 仓库阅读、文档、后续变更目标识别
- **依据：** `docs/sprints/sprint-documentation-baseline.md` 的硬锚点与仓库取证

## 背景

仓库顶层同时保留 `Fall from Heaven 2`、`Streak`、`Streak 3` 与 `Rampage` 四套覆盖内容。后续维护需要一个主要阅读入口，否则相同文件名和不同年代的规则会导致证据混用；但仓库只能说明版本库内容，不能观察用户机器的游戏进程、模组目录或被加载 DLL。

谱系事实：

- `5b397cd` 添加 FFH2 Patch o 基线。
- `0786ba6`、`bc6bf41`、`4c9a642` 依次添加 Streak、Streak 3、Rampage。
- 在各自添加提交中抽样，Streak 的单位 XML/事件管理器与 FFH2 相同；Streak 3 的单位 XML 与 FFH2 相同、DLL 与 Streak 相同；Rampage 的单位 XML/事件管理器/DLL 与 Streak 3 相同，C++ `CvUnit.cpp` 与 FFH2 相同。
- `Rampage` 同时包含 C++ 源码、XML、Python、Art、res 和预编译 DLL，其路径最后提交为 `49d4af0`（2016-01-26）；其他三条路径的最后提交更早。
- 四套 `installpatch.bat` 都复制到仓库外的既有模组目录；场景文件还可通过 `ModPath` 指向别的模组。

## 决策

后续架构、接口和规则理解默认从 `Rampage` 取证，并把另外三个目录用于基线对照、历史归因和回归差异分析。

[产品定义](../../product/product-definition.md) 与 [PRD](../../product/PRD.md) 进一步把 `Rampage/` 和 `Mods\Rampage` 规定为产品权威代码线与目标目录。该规范决定系统应该交付什么；本决策约束的是证据语言：规范目标不等于某台用户机器已经加载该目标。

所有关于目标代码线的表述必须使用“仓库重点”“最后演化代码线”或等价的版本库语义。除非取得用户机器上的运行证据，不得称 `Rampage` 为“当前运行模组”“已安装目标”“生产版本”或“实际加载版本”。

需要修改或验证运行行为时，先独立确认以下三项：

1. 游戏启动所选择的模组目录。
2. 该目录中实际被加载的 `CvGameCoreDLL.dll` 身份或哈希。
3. 覆盖后的 XML、Python 与资源集合来自哪条代码线和哪份基础安装。

## 备选方案

| 方案 | 阅读复杂度 | 误改风险 | 运行态准确性 | 评估 |
|---|---:|---:|---:|---|
| 四个目录等权并行理解 | 高 | 高；同名规则容易互相污染 | 不增加 | 不采用；保留谱系对照但缺少维护入口 |
| 以 Rampage 为仓库重点，并显式保留运行态未知 | 中 | 低；目标清晰且证据边界明确 | 不虚构 | 采用 |
| 直接把 Rampage 声明为用户运行目标 | 低 | 极高；可能诊断或修改错误目录 | 低 | 不采用；仓库证据不足 |
| 只保留 Rampage，忽略其他目录 | 低 | 中；丢失来源和差异证据 | 不增加 | 不采用；历史目录仍有基线价值 |

## 权衡

采用 Rampage 焦点能降低日常阅读成本，并让完整 C++/XML/Python/资源链成为统一证据面；代价是每个结论都需要区分“Rampage 规则”与“共享 FFH2/Streak 规则”，不能把目录年代自动当成产品权威性。

保留运行态未知会增加一次目标确认步骤，但避免最昂贵的错误：在错误目录修复、用错误 DLL 验收，或把场景 `ModPath` 路由到 FFH2 的行为误判为 Rampage 行为。

## 后果

- [架构总览](../overview.md)、技术栈、接口文档和通用方法索引以 Rampage 路径作为默认证据来源。
- 历史比较按 `Fall from Heaven 2 → Streak → Streak 3 → Rampage` 的内容谱系组织，但不把这条箭头解释为 Git 分支关系。
- 运行问题报告必须记录模组路径、DLL 身份和基础文件集合；只给出仓库分支或目录名不构成运行证据。
- 任何仅存在于旧目录、但不存在于 Rampage 的行为都标为历史差异，而不是自动纳入 Rampage 架构。
- 当用户明确指定另一条代码线时，以用户指定目标为准，同时继续使用运行证据确认原则。

## 失效条件

出现以下任一证据时，应重新评估本决策：

- 用户指定并证实长期维护目标是另一目录。
- 新提交在另一代码线继续演化并形成更完整的跨层内容。
- 外部发行清单或可复现构建证明另一目录才是权威发布源。

这些条件改变的是“仓库理解重点”，不会取消“仓库不能单独证明用户运行态”的证据边界。
