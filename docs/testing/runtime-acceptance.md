# Rampage Windows 运行验收指南

## 定位与权威边界

本文是未来 Windows 执行的环境、冒烟和场景验证指南，不是 Sprint 验收标准，也不记录当前是否通过。产品预期以 [PRD](../product/PRD.md) 的 AC-F001～AC-F007 为准，固定字段与入口以[跨层接口契约](../api/README.md)为索引；正式验收时，tester 只消费 Scrum Master 编写并经产品复核的验收标准、批次和场景分母，按指定验收流程产出报告。

本页不授权在当前 macOS 工作区启动游戏，不创建测试用户、Web/API/DB 测试或截图报告。

## 执行顺序

```text
Windows 宿主基线
  → 完整 FFH2 Patch o 基线
  → 干净 Rampage staging 与身份核对
  → Rampage 加载冒烟
  → 五项核心机制 F002–F006
  → F007 跨界面对账
  → 存档/重载与部署回归
```

任一层失败即停止向上授予结论，保留现场并按最先失败层诊断。部署、备份、恢复和 DLL 构建的操作步骤以[服务生命周期](../ops/services.md)为准。

## 证据清单

每个批次开始前建立一次环境清单：

- Windows 版本、机器/虚拟机标识和本地时间。
- Civ4、BtS、FFH2 Patch o 的版本、来源与绝对安装路径。
- Rampage 绝对路径、来源提交、部署清单、是否由干净基线创建。
- 实际 `CvGameCoreDLL.dll` 的 SHA-256、PE 架构、Debug/Release 或预编译来源。
- 构建时的工具链版本、完整日志、PDB 与产物清单；未重建时明确记录源码同源性未知。
- Python/XML 日志位置、缓存处理方式、场景/地图/速度/难度/随机种子。
- 每个场景的起始存档、关键回合存档、操作序列、可见数值、战斗日志及必要截图/录像。

只有目录名或主菜单截图不能证明实际 DLL、合并资产和规则身份。

## R0：外部宿主基线冒烟

按隔离顺序验证：

1. Civilization IV 能启动到主菜单并正常退出。
2. Beyond the Sword 能启动、新建最小对局、进入地图并正常退出。
3. 完整 `Fall from Heaven 2` Patch o 能独立加载、新建最小对局、进入地图并保存/重载。
4. 保存各阶段日志，并确认没有把 Rampage 文件提前覆盖进基线。

对应 PRD：AC-F001-01。任何一步失败时，问题属于外部基线或环境，不能用 Rampage 修改绕过。

## R1：构建与干净 staging

### 可选源码构建门禁

在匹配的隔离 Windows 工具链中执行：

```bat
cd /d <Rampage源码绝对路径>\Assets\src\CvGameCoreDLL.041o
nmake /NOLOGO Debug_clean
nmake /NOLOGO Debug
nmake /NOLOGO Release_clean
nmake /NOLOGO Release
```

逐命令保存完整输出和退出码；确认 Win32/x86 DLL、Debug PDB、源提交、工具链和 SHA-256。Makefile 自动复制目标必须指向一次性 staging，不能指向已验证或正式模组目录。构建通过不代表 BtS 能装载。

### 合并目标身份

1. 从已验证的完整 FFH2 Patch o 复制一个独立、干净的 `Rampage` 目录。
2. 用绝对路径合并仓库 Rampage 的 XML、Python、Art、res 和 DLL；不把 `Assets/src` 当作运行资产。
3. 记录合并文件清单、DLL 前后哈希、外部基线保留文件和缓存策略。
4. 在合并结果上重跑 XML well-formed、Schema/Type/文本/资源引用检查。
5. 确认游戏实际选择的模组目录、实际 DLL 哈希和加载日志均指向该 staging。

对应 PRD：AC-F001-02、AC-F001-04。覆盖包缺少的文件必须由这份已验证基线提供，不能从另一个不明安装中临时拼接。

## R2：Rampage 加载与入口冒烟

1. 从 BtS 的“高级 → 加载模组”选择 Rampage，记录重启后的模组名和日志。
2. 进入主菜单后创建最小测试局，分别确认 Air、Earth、Fire、Water 氏族入口可见并可进入地图。
3. 打开 HUD、选中单位、文明百科单位页、财务顾问和战斗日志入口。
4. 观察 XML/Python 错误、缺失文本键、粉色/缺失资源、界面崩溃或 DLL 加载异常。
5. 保存启动后最小存档，退出并重载一次。

对应 PRD：AC-F001-02、AC-F001-03、AC-F001-04，以及 F007 的入口前提。这里只建立可测试性，不因“能进地图”推定五项机制正确。

## R3：五项核心机制

以下是执行场景族和取证点，不改写产品预期。具体输入、数值和 PASS/FAIL 判定必须引用 PRD 及 SM 的权威验收标准。标注“静态风险定向”的场景只用于验证源码候选风险，不表示问题已复现，也不构成验收标准或正式 TC。

### M1 多属性多掷骰近战（F002）

| 场景族 | PRD 对应 | 最小设置与操作 | 必取证据 |
|---|---|---|---|
| 属性差异 | AC-F002-01 | 用只改变生命/护甲/敏捷/近战强度之一的成对单位攻击同一目标 | 双方单位面板、战前预览、逐次日志、战后生命 |
| 多次掷骰 | AC-F002-02 | 选择攻击次数大于 1 的单位，记录一次攻击中的所有 roll | 每次命中/落空、骰值/门槛、伤害、总次数 |
| 同轮致死停止（静态风险定向） | AC-F002-02、AC-F007-02 | 从可重复存档构造防守方在本轮先掷骰、能对攻击方造成致死伤害且攻击方仍有攻击次数的近战 | 防守方致死事件前后的逐次日志、双方生命与伤害；对照“任一方死亡立即停止”，确认攻击方同轮是否仍掷骰或造成伤害 |
| 护甲与最低伤害 | AC-F002-03 | 用不同护甲目标和能触发下界的伤害组合对照 | 原始/最终伤害可见证据、剩余生命 |
| 受伤强度 | AC-F002-04 | 同单位满血与受伤状态分别攻击等价目标 | 攻击前生命、预览、roll 结果与战后状态 |
| 行动成本与日志 | AC-F002-05 | 攻击前后记录移动/行动状态，并对账日志 | 行动状态、日志顺序、击败结果、回合末状态 |

使用固定地图、固定单位配置和可重复存档；随机机制用足以覆盖权威场景分母的重复次数，不用单次结果推导概率实现。

### M2 最小/最大距离远程打击（F003）

| 场景族 | PRD 对应 | 最小设置与操作 | 必取证据 |
|---|---|---|---|
| 距离边界 | AC-F003-01 | 在最小距离内、恰好最小/最大距离、最大距离外分别选目标 | 地块坐标/距离、目标合法性、动作反馈 |
| 无视视线 | AC-F003-02 | 保持距离合法，分别用无遮挡和被地形/单位遮挡的目标 | 地图布局、目标高亮、提交结果、日志 |
| 多次射击与击败 | AC-F003-03 | 使用多次远程攻击单位，对存活与中途击败目标取证 | 每次射击、停止条件、最终生命/移除状态 |
| 行动成本 | AC-F003-04 | 记录远程动作前后移动力、攻击次数和同回合可用动作 | 单位面板、动作栏、日志、回合末状态 |

同时验证无效目标不会偷偷扣除行动资源；预期仍取自权威验收标准。

### M3 基于回合起点的 `plotDistance` 移动半径与地块容量（F004）

以下场景按[测试计划](./test-plan.md)定义的近似八边形 `plotDistance` 边界取点，不按欧氏圆取点。

| 场景族 | PRD 对应 | 最小设置与操作 | 必取证据 |
|---|---|---|---|
| `plotDistance` 半径边界 | AC-F004-01 | 从同一回合起点向轴向、对角和半径边界外地块规划移动 | 回合起点、目标坐标、`plotDistance`、可达性、实际终点 |
| 回合重置 | AC-F004-02 | 移动后结束回合，再比较新回合边界 | 两个回合的起点、范围和移动记录 |
| 标准容量 | AC-F004-03 | 逐个向同一地块加入普通单位直到边界，再尝试超限 | 地块单位清单、合法性反馈、实际占用数 |
| 运输货物容量（静态风险定向） | AC-F004-03 | 使用同一正成本运输者，分别空载和装载可防守、正成本货物，尝试进入相同的临界容量地块 | 地块容量、运输者与货物成本清单、空载/装载允许或拒绝结果、进入后的实际占用 |
| 城市临界训练（静态风险定向） | AC-F004-03 | 控制城市地块现有占用与候选单位成本，使二者之和分别低于、等于和高于容量，再尝试训练并推进到完成 | 现有占用、候选成本、容量、训练资格、完成结果与完成后实际占用 |
| 例外单位 | AC-F004-04 | 对权威标准列出的例外单位重复容量边界 | 单位类别、地块清单、允许/拒绝结果 |
| 容量来源 | AC-F004-05 | 在地形/特征/改良等权威组合间对照 | 地块详情、容量来源、单位清单与操作结果 |

边界应覆盖移动预览、实际命令和 AI/城市训练等受影响入口，避免只验证一种入口。

### M4 工人占格生产（F005）

| 场景族 | PRD 对应 | 最小设置与操作 | 必取证据 |
|---|---|---|---|
| 首名工人 | AC-F005-01 | 记录无工人地块，首名 Worker 进入并执行权威动作 | 地块/HUD/顾问前后数值、动作状态、回合结算 |
| 不叠加 | AC-F005-02 | 第二名及更多 Worker 进入同地块 | 每次进入后的单位清单与产出明细 |
| 最后离开 | AC-F005-03 | 多 Worker 逐个离开，包含最后一名离开 | 每步地块占用、产出和玩家汇总 |
| 产出变化 | AC-F005-04 | 在权威地块/改良/状态组合下进入、停留、离开 | 原始值、变化来源、最终值、事件/文本反馈 |
| Work Tile 保存/重载（静态风险定向） | AC-F005-01、AC-F005-03、AC-F007-03 | 让首名 Worker 在合格地块产生贡献，保存后完全退出游戏进程并重载；在移动单位或推进回合前取证，再令最后一名 Worker 离开并推进一回合 | 存档与 DLL 身份；保存前/重载后的地块 `isWorked()` 原生值、玩家 `COMMERCE_GOLD`/`COMMERCE_FOOD`、Food Stores 与 Worker 坐标；离开后的撤销值和下一回合结算 |

至少跨一个回合，并在关键状态保存/重载，防止 UI 临时显示与持久规则不一致。

Work Tile 保存/重载定向场景必须通过调试器/PDB 或等价原生取证读取地块 worked 标记，并与玩家账本和 Worker 坐标同步对账；HUD、顾问或地块图标只能作为辅助证据，不能单独证明状态恢复正确。该场景用于核对静态风险，不预设重载后的具体故障表现。

### M5 玩家级食物经济（F006）

| 场景族 | PRD 对应 | 最小设置与操作 | 必取证据 |
|---|---|---|---|
| 军事成本 | AC-F006-01 | 按权威单位组合逐个增减计费单位 | 单位清单、Food Income/Cost/Stores、净值 |
| 豁免条件 | AC-F006-02 | 分别令玩家处于无政府、禁用生产或启用“无维护”条件，并逐一计算食物成本 | 无政府状态、生产禁用状态、“无维护”选项值与 HUD/财务顾问 Food Cost 对账 |
| 正净食物 | AC-F006-03 | 构造收入高于成本的回合并结束回合 | 结算前后储备、收入、成本、金币 |
| 负净值但储备足够 | AC-F006-04 | 构造成本高于收入且储备足够的回合 | 结算前后储备与金币、公式对账 |
| 食物缺口 | AC-F006-05 | 构造储备不足的缺口并结束回合 | 缺口、储备归零、金币变化和日志/提示 |
| 食物存档持久化（静态风险定向） | AC-F006-03 至 AC-F006-05、AC-F007-03 | 构造非零 Food Stores、Income、Cost，记录后保存，完全退出游戏进程，再启动并重载该存档；先在推进回合前对账三项，再推进一回合复算 | 存档与 DLL 身份、退出进程证据、保存前/重载后 Food Stores/Income/Cost、下一回合储备与金币变化 |
| 禁用研究状态下 Food Income/净食物（静态风险定向，产品意图未知） | AC-F006-03 至 AC-F006-05、AC-F007-03 | 在 `COMMERCE_FOOD` 非零时保持 Worker、军事成本和其他食物修正不变，成对记录禁用研究关闭/开启状态，并各推进一回合 | `getDisableResearch()` 状态、原始食物 commerce、财务顾问 Food Income、HUD 净食物、Food Cost、结算前后 Food Stores/金币；只记录耦合是否发生，不代替产品侧定义预期 |

每个结算场景都保存回合前存档，重复加载并复算一次；对账使用原始整数值，不用格式化文本替代数据。

当前源码未见 `m_iFoodPerTurn` 的非零写入入口。若受支持运行环境也无法通过既有玩法或脚本构造该修正，应保留“来源未知”的静态风险，不通过测试注入臆造产品入口；Food Stores/Income/Cost 的保存→退出进程→重载对账仍必须执行。

## R4：F007 原生信息对账

F007 不是独立规则算法，而是对核心机制的可见反馈闭环：

| 对账组 | PRD 对应 | 必须比较的视图 |
|---|---|---|
| 单位信息 | AC-F007-01 | Unit XML/权威配置、文明百科、选中单位面板、战斗预览 |
| 战斗结果 | AC-F007-02 | 战前预览、逐次战斗日志、战后单位生命/状态、击败结果 |
| 食物账目 | AC-F007-03 | HUD、财务顾问、回合前后 Stores/Income/Cost、金币变化 |

同一数值在多个视图出现时全部一致才构成对账证据。界面一致但规则错误，或规则正确但界面错误，均需定位到相应层，不能互相抵消。

## R5：存档与部署回归

在权威场景分母覆盖完成后追加：

1. 在 F004/F005/F006 的关键中间状态保存、完全退出游戏进程、重载并继续一个回合；F005 Work Tile 必须在任何移动或回合推进前同步记录地块 worked 原生值、玩家金币/食物 commerce、Food Stores 与 Worker 坐标，再令最后一名 Worker 离开验证贡献只撤销一次，不能只看 UI；F006 必须逐项记录保存前与重载后的 Food Stores/Income/Cost，再对账下一回合储备和金币。
2. 对同一来源分别建立“完整基线新建的干净 staging”和“按批准清单更新的 staging”，比较文件清单、哈希和核心冒烟。
3. 清理或保留缓存的策略必须显式记录，并验证不会用旧缓存掩盖 XML/Python 变化。
4. 核对所有场景 `ModPath`；指向其他模组的场景不得当作 Rampage 证据。
5. 用上一个已验证 DLL/覆盖目录执行最小对照，确认回退备份可恢复，而不是使用 Git 回退游戏目录。

## 失败时的分层定位

按以下顺序收集证据，指出第一处不一致：

| 诊断层 | 检查 | 典型证据 |
|---|---|---|
| D0 身份/基线 | 模组路径、DLL 哈希、合并清单、缓存、场景路由 | 清单与 SHA-256 |
| D1 XML/资源 | well-formed、Schema/Type/文本/资源闭包 | 解析错误、引用差异、加载日志 |
| D2 DLL/规则 | 构建来源、ABI、XML 读取、规则状态 | 构建日志、Debug/PDB、原生日志 |
| D3 Cy*/事件/Python | 方法/枚举、模块函数、参数顺序、导入闭包 | PythonErr/PythonDbg、调用证据 |
| D4 UI/交互 | 控件入口、显示转换、动作提交 | 截图/录像、UI 日志 |
| D5 玩家行为 | 最终规则、跨回合与存档结果 | 测试存档、逐回合对账 |

D1 通过不能证明 D2，D3 有值不能证明 D4 正确，截图正确也不能证明 D0–D3 身份和计算正确。先修复或隔离最低失败层，再重复其上所有受影响场景。

## 停止与升级条件

- Civ4/BtS/FFH2 任一基线冒烟失败：停止 Rampage 验证，交 DevOps/环境维护者。
- 目标绝对路径、DLL 哈希、源码来源或合并清单无法确认：停止，禁止出具玩法结论。
- XML/Python 加载错误、崩溃、存档损坏或跨层数据不一致：保留失败目标和日志，恢复部署前备份，不继续扩大场景。
- 预期与 PRD/SM 验收标准冲突：tester 不自行改写预期，返回 Scrum Master/产品经理澄清。
- 正式验收中同一 TC 的重试和 BLOCKED 规则以 SM 派单及验收流程为准；本文不另建一套判定制度。
