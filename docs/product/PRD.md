# Rampage 产品需求文档

## 文档定位

本文把 [产品定义](./product-definition.md) 转换为可测试的功能契约。原生游戏界面与交互细节见 [UE 交互规格](./UE-spec.md)，文档演变见 [变更日志](./changelog.md)。

### 规范用语

- “必须”表示产品行为契约。
- “事实依据”表示仓库静态证据，不等价于 Windows 运行验收结论。
- “未知”表示需要运行环境或产品决策补齐的信息。
- P0 表示核心玩法不可缺少；P1 表示解释与可观察性不可缺少，但不改变底层结算规则。

## 目标

1. 让玩家在一个兼容的原生 Civilization IV 模组入口中选择四个元素氏族并进入普通对局。
2. 让近战和远程战斗由明确的单位属性、攻击次数、命中判断和伤害反馈组成。
3. 让基于回合起点的 `plotDistance` 移动半径、地块容量、工人部署和军队食物消耗形成相互制约的战术经济循环。
4. 让所有核心规则都能从原生 HUD、单位面板、预览、日志、财务顾问或文明百科得到可观察证据。

## 用户故事

- 作为战术玩家，我想在攻击前看到双方命中概率、伤害、攻击次数和生命，以便决定是否交战。
- 作为远程单位使用者，我想知道最小/最大射程和每次动作的射击次数，以便选择站位和目标。
- 作为阵地指挥者，我想让回合位移和地块容量阻止绕路超程与无限堆叠，以便战线和通道具有意义。
- 作为经济管理者，我想通过部署工人获得地块食物与商业，并看到军队的食物成本，以便平衡扩军和储备。
- 作为模组维护者，我想让 XML 数值、C++ 结算和 Python 界面使用同一组字段，以便改动可以被验证。

## F001 外部运行依赖与元素氏族入口

### 功能定义

- Rampage 必须作为 `Mods\Rampage` 下的覆盖包加载，并与同一套 DLL、XML、Python、Art、res 内容配合。
- 运行环境必须先提供 Civilization IV: Beyond the Sword 与 Fall from Heaven 2 Patch o 的基础模块和资源。
- 游戏设置必须向玩家提供 Air、Earth、Fire、Water 四个可选氏族。
- Barbarian 必须保留为系统文明，不出现在玩家可选氏族集合中。
- `Fall from Heaven 2`、`Streak`、`Streak 3` 只用于谱系参考，不参与 Rampage 的运行时合并。
- 遗留场景、事件、法术和单位类别只有在引用完整与运行验收同时成立时，才可作为可玩入口；存在文件本身不构成产品承诺。

### 验收标准

**AC-F001-01 外部依赖**

- Given 一台仅有本仓库文件、没有 Beyond the Sword 与 FFH2 基础安装的机器
- When 尝试把 Rampage 当成独立程序运行
- Then 该环境不属于受支持运行条件，验收不得宣称覆盖包可独立运行

**AC-F001-02 模组加载**

- Given 兼容的 Windows Beyond the Sword、FFH2 Patch o 基础内容和 `Mods\Rampage` 目录
- When 按覆盖契约放置 DLL、XML、Python、Art 和 res 并从游戏加载 Rampage
- Then 游戏应使用 Rampage 的跨层契约进入模组界面，不得混用其他顶层目录的同名文件

**AC-F001-03 氏族选择**

- Given Rampage 的普通游戏设置界面
- When 玩家选择文明
- Then Air、Earth、Fire、Water 可选，Barbarian 不可选

**AC-F001-04 遗留入口**

- Given 一个引用 Rampage 文明表中不存在类型的场景或事件
- When 评估其产品可用性
- Then 结果必须记为未被产品承诺，不能仅凭文件存在判定可用

### 依赖与风险

- 外部基础安装提供仓库缺少的 Python 模块、美术资源与全局定义。
- 预编译 DLL 是 32 位 Windows PE 文件。
- 仓库证据不能确认用户机器实际加载的模组目录。

## F002 多属性多掷骰近战

### 功能定义

- 每种战斗单位必须由最大生命、护甲、敏捷、近战强度和近战攻击次数定义。
- 单次近战中，攻击方与防守方各自按攻击次数获得掷骰机会，任一方死亡时立即结束剩余掷骰。
- 一方命中另一方的概率必须由目标的敏捷/闪避值及战斗修正决定；更高目标闪避应降低命中概率。
- 单次命中伤害必须反映攻击方强度、目标护甲与战斗修正，并保持至少 1 点正伤害。
- 受伤不得按剩余生命比例削减单位的战斗强度；生命只决定还能承受多少伤害。
- 一次近战动作必须消耗攻击单位的全部剩余移动力。
- 命中、落空、骰值、命中门槛、伤害、剩余生命和击败结果必须进入双方可见的战斗日志。

### 验收标准

**AC-F002-01 属性差异**

- Given 两组仅敏捷、护甲、生命或攻击次数不同的单位
- When 分别查看单位资料并执行足量可重复战斗
- Then 这些字段应分别影响承伤上限、单次伤害、命中分布或掷骰次数，且不能被合并成单一强度字段

**AC-F002-02 多次掷骰**

- Given 攻击次数大于 1 的攻击方或防守方
- When 双方进入近战且没有在首个掷骰后死亡
- Then 日志应出现与各自可用攻击次数相符的连续命中/落空事件，直到次数耗尽或一方死亡

**AC-F002-03 护甲与最低伤害**

- Given 同一攻击单位分别攻击低护甲与高护甲目标
- When 两次攻击均命中且其他修正一致
- Then 高护甲目标承受的单次伤害不高于低护甲目标，正伤害不低于 1

**AC-F002-04 受伤强度**

- Given 同一单位分别处于满生命和受伤状态，且其他修正一致
- When 查看并计算其攻击强度
- Then 两种状态使用同一战斗强度，只有剩余承伤空间不同

**AC-F002-05 移动力与日志**

- Given 一个仍有移动力的单位向合法敌方目标发起近战
- When 战斗结算
- Then 攻击方剩余移动力归零，日志逐次显示骰值/门槛、命中或落空、伤害及剩余生命

### 依赖与风险

- **产品目标**：任一方死亡时立即停止剩余掷骰，不允许已死亡单位继续产生同轮攻击、伤害或日志。
- **静态事实**：`resolveCombat` 在每轮中先处理防守方掷骰与对攻击方的伤害，再处理攻击方掷骰与对防守方的伤害，之后才统一检查双方是否死亡并退出循环（`CvUnit.cpp:1790-2016`）。
- **推断风险**：若防守方在本轮先使攻击方死亡，攻击方分支仍可能在死亡检查前继续执行，因而可能与“死亡立即停止”目标漂移。
- **运行未知**：该控制流是否会在实际 DLL 中产生死亡后的同轮反击、伤害或日志尚未复现，需在 Windows 游戏环境用可控生命与伤害场景验证。

### 事实依据

`Rampage/Assets/XML/Units/CIV4UnitSchema.xml:350-357`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvUnit.cpp:1750-2049,2235-2253,9691-9705,10322-10463`；`Rampage/Assets/python/CvEventManager.py:602-682`。

## F003 最小/最大距离远程打击

### 功能定义

- 具备远程能力的非空中单位必须由远程强度、远程攻击次数、最小距离和最大距离定义。
- 远程动作只能选择距离处于闭区间 `[最小距离, 最大距离]` 且拥有合法敌方防守者的地块。
- 地形或单位造成的视线阻挡不得使区间内的合法目标失效。
- 每次远程动作必须按远程攻击次数逐次掷骰；命中概率由目标敏捷/闪避决定；每次命中施加远程伤害。
- 远程伤害可以击败目标；目标死亡后停止剩余射击。
- 远程动作必须消耗攻击单位全部剩余移动力，并产生与近战同构的命中/落空日志。

### 验收标准

**AC-F003-01 距离边界**

- Given 一个最小距离为 `m`、最大距离为 `n` 的远程单位和合法敌方防守者
- When 分别选择距离 `m-1`、`m`、`n`、`n+1` 的目标地块
- Then 仅 `m` 与 `n` 的目标可执行远程动作

**AC-F003-02 无视视线**

- Given 一个距离合法且有敌方防守者、但直线被地形阻挡的目标
- When 玩家执行远程动作
- Then 视线阻挡本身不应拒绝目标

**AC-F003-03 多次射击与击败**

- Given 远程攻击次数大于 1 的单位和能承受至少一次命中的目标
- When 执行远程动作
- Then 日志逐次记录射击；若目标生命降至 0 则标记击败并停止后续射击

**AC-F003-04 行动成本**

- Given 一个有剩余移动力且能执行远程动作的单位
- When 远程结算完成
- Then 剩余移动力归零

### 依赖与风险

- 基础安装提供 `RANGED_ATTACKS_USE_MOVES` 等全局定义；其具体值属于运行验收项。
- XML 同时为 `Work Tile` 与远程目标模式声明 `B` 键，实际上下文分派需在游戏中确认。

### 事实依据

`Rampage/Assets/XML/Units/CIV4UnitInfos.xml:1405-1546,1847-1988,2066-2207,2285-2645`；`Rampage/Assets/XML/Interface/CIV4InterfaceModeInfos.xml:286-305`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvUnit.cpp:19352-19631`。

## F004 基于回合起点的 `plotDistance` 移动半径与地块容量

### 功能定义

- 每个单位在回合开始时必须记录回合起点。
- 单位只能进入与回合起点的 `plotDistance` 不大于其最大移动格数的地块；路径弯折不得扩大该 `plotDistance` 边界。
- 普通移动仍必须扣除实际地块移动成本；进入敌方相邻控制区必须结束移动。
- 每个地块必须由地形容量、地物容量、改良容量、丘陵修正与城市容量共同决定驻留上限。
- 每个可防守单位必须有地块成本；陆地单位与飞行单位分别计入相应容量；运输货物按规则计入。
- 成本为 0 或不能防守的单位不应因容量被拒绝。
- 非攻击性进入或进入友方城市时，如果加入后的有效成本超过可用容量，移动必须被拒绝。
- 城市训练军事单位的资格必须接受城市地块容量约束；边界等值行为列入未知项。

### 验收标准

**AC-F004-01 plotDistance 边界**

- Given 一个最大移动格数为 `r` 的单位位于回合起点
- When 玩家通过直线或曲折路径尝试进入与起点 `plotDistance` 为 `r+1` 的地块
- Then 目标始终不可进入，即使累计移动成本仍有余额

**AC-F004-02 回合重置**

- Given 单位在上一回合移动到新地块
- When 新回合开始
- Then 新地块成为新的回合起点，`plotDistance` 从该地块重新计算

**AC-F004-03 标准容量**

- Given 容量为 100 的普通地块和地块成本为 50 的标准可防守单位
- When 两个单位依次进入
- Then 两个单位可驻留；第三个同成本单位的非攻击性进入被拒绝

**AC-F004-04 例外单位**

- Given 地块已达到可防守单位容量
- When 成本为 0 或不能防守的单位尝试进入
- Then 容量规则本身不应拒绝该单位

**AC-F004-05 容量来源**

- Given 两个仅地形、地物、改良、丘陵或城市属性不同的地块
- When 查询并消耗其容量
- Then 上限必须由各来源值相加得到，不能只按单位数量硬编码

### 依赖与风险

- **产品目标**：运输货物按规则计入地块占用；城市训练资格按“现有占用 + 候选单位成本”约束训练后的容量边界。
- **静态事实**：`hasMaxUnitPerTile` 把运输货物成本累加到 `iActualUnitWithCargo`，但后续容量拒绝只使用 `iLandUnitCost`、`iFlyingUnitCost` 与容量值，未再读取该货物变量（`CvUnit.cpp:3449-3578`）。
- **推断风险**：运输货物的地块成本可能没有实际影响移动时的容量拒绝，与“运输货物按规则计入”目标漂移。
- **运行未知**：运输工具携带不同成本、不同可防守状态货物时，容量拒绝是否变化尚未复现，需在 Windows 游戏环境验证。
- **静态事实**：`CvCity::canTrain` 读取城市地块当前陆地/飞行占用并与容量比较；候选单位成本只用于判断是否进入容量检查，未加到现有占用后再比较（`CvCity.cpp:1834-1870`）。
- **推断风险**：接近容量边界的城市可能允许训练一个使完成后占用超限的候选单位。
- **运行未知**：训练资格、队列反馈、完成生成以及等于/超过容量边界的最终行为尚未复现，需在 Windows 游戏环境验证。

`Rampage/Assets/src/CvGameCoreDLL.041o/CvUnit.cpp:1303-1309,3439-3641,4208-4226`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvPlot.cpp:3423-3486`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvCity.cpp:1834-1870`；`Rampage/Assets/XML/Terrain/CIV4TerrainInfos.xml:28-30`；`Rampage/Assets/XML/GlobalDefinesAlt.xml:434-452`。

## F005 工人占格生产

### 功能定义

- Worker 必须拥有 `Work Tile` 能力；该能力仅在建造前置条件满足的地块上有效。
- 工人进入合格地块时，首名同类型工人必须把该地块的商业产出计入玩家金币商业，把食物产出计入玩家食物商业，并将地块标记为被工作。
- 同一合格地块上的额外同类型工人不得重复计入产出。
- 最后一名同类型工人离开合格地块时，先前贡献必须撤销，并清除被工作标记。
- 工人在地块上执行改变产出的建造动作时，玩家收入必须先移除旧产出、再计入新产出，避免重复累计。
- 占格变化必须刷新 HUD、城市、财务顾问和信息面板。

### 验收标准

**AC-F005-01 首名工人**

- Given 一个满足 `Work Tile` 条件、具有可观察食物与商业产出的地块
- When 首名 Worker 进入该地块
- Then 玩家食物与金币商业按地块产出增加，地块进入被工作状态

**AC-F005-02 工人不叠加**

- Given 一个已经由 Worker 贡献产出的地块
- When 第二个同类型 Worker 进入或其中一个离开但仍有同类型 Worker 留下
- Then 玩家收入保持不变

**AC-F005-03 最后离开**

- Given 一个只有一名 Worker 的工作地块
- When Worker 离开
- Then 对应食物与金币商业贡献撤销，地块不再标记为被工作

**AC-F005-04 产出变化**

- Given Worker 驻留在工作地块并执行会改变地块产出的建造动作
- When 动作更新地块产出
- Then 玩家账面只反映新产出一次，不保留旧产出或重复新产出

### 依赖与风险

- **依赖**：`Work Tile` 是否可用由单位建造表、科技前置与地块条件共同决定。
- **产品目标**：被工作地块标记、实际 Worker 位置与玩家食物/金币商业账本必须表达同一占格生产状态。
- **静态事实**：`m_bIsWorked` 只见构造初始化、`setWorked` 写入与 `isWorked` 读取接口；`CvPlot::read` 和 `CvPlot::write` 未见该成员的流读写，仓库内也未见 `isWorked()` 被其他规则消费（`CvPlot.h:512-513,659`；`CvPlot.cpp:74,4880-4888,9181-9420,9426-9667`；`CvUnit.cpp:1534,1541`）。
- **推断风险**：保存/重载可能使地块标记、已保存的 Worker 位置与玩家商业账本通过不同恢复路径形成不一致，但静态证据不能确定具体表现。
- **运行未知**：存在工作地块时保存并完全重载后，三类状态能否继续一致，以及最后一名 Worker 离开是否只撤销一次贡献，均需在 Windows 游戏环境验证；长时间建造完成后的离格行为与视觉标记同样属于运行确认项。

### 事实依据

`Rampage/Assets/XML/Units/CIV4BuildInfos.xml:593-610`；`Rampage/Assets/XML/Units/CIV4UnitInfos.xml:304-309`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvPlot.cpp:74,4880-4888,9181-9667`；`Rampage/Assets/src/CvGameCoreDLL.041o/CvUnit.cpp:1477-1566,8407-8446,12671-12681`。

## F006 玩家级食物经济

### 功能定义

- 玩家必须拥有独立于城市粮仓的玩家级食物储备与每回合食物变化率。
- 玩家食物收入必须由 `COMMERCE_FOOD` 收入与其他每回合食物修正相加得到。
- 正常维护条件下，每个军事单位消耗 1 食物，并叠加额外单位成本。
- 无政府状态、禁用生产或“无维护”游戏选项下，军事食物成本为 0。
- 每回合净食物等于食物收入减军事食物成本，并计入玩家食物储备。
- 若结算后储备低于 0，每缺少 1 食物必须扣除 5 金币，然后把食物储备归零；该规则不以城市饥荒或自动解散单位替代。
- HUD 必须显示食物储备与净变化；财务顾问必须分列食物储备、食物收入和食物成本。

### 验收标准

**AC-F006-01 军事成本**

- Given 正常维护条件下玩家拥有 `n` 个军事单位且额外单位成本为 `e`
- When 计算食物成本
- Then 结果为 `n + e`

**AC-F006-02 豁免条件**

- Given 玩家处于无政府、禁用生产或启用“无维护”任一条件
- When 计算食物成本
- Then 结果为 0

**AC-F006-03 正净食物**

- Given 食物收入大于食物成本
- When 回合结算
- Then 储备按差额增加，金币不因食物结算减少

**AC-F006-04 负净食物但储备足够**

- Given 本回合净食物为负且结算后的储备仍不低于 0
- When 回合结算
- Then 储备按差额减少，金币不因食物结算减少

**AC-F006-05 食物缺口**

- Given 结算前储备与本回合净食物相加为 `-d`，其中 `d > 0`
- When 回合结算
- Then 金币减少 `5 × d`，食物储备变为 0，不触发城市饥荒或自动解散单位作为替代行为

### 依赖与风险

- **产品目标**：玩家级食物储备和每回合修正必须持续参与跨回合经济，并在受支持的保存/重载流程中保持一致。
- **静态事实**：`m_iFood`、`m_iFoodPerTurn` 在玩家重置时归零；`CvPlayer::read` 与 `CvPlayer::write` 未见针对二者的流读写（`CvPlayer.h:1184-1185`；`CvPlayer.cpp:416-417,16813-17328,17334-17800`）。
- **静态事实**：`m_iFoodPerTurn` 在仓库内只见初始化为 `0`、C++ getter 与 Cy 只读暴露，未见 setter、change 或其他非零写入来源（`CvPlayer.cpp:417,7181-7189,8737-8739`；`CyPlayer.cpp:805-807`；`CyPlayerInterface1.cpp:189`）。
- **推断风险**：玩家级 Food Stores 或外部来源提供的每回合修正可能无法跨保存/重载保持；仓库自身也可能无法产生非零的 `m_iFoodPerTurn` 输入。
- **运行未知**：保存/重载后的 Food Stores、净变化与每回合修正保留行为，以及运行包是否提供仓库外修正来源，均未复现，需在 Windows 游戏环境验证；静态证据不足以断言具体丢失表现。
- **静态事实**：`CvPlayer::getCommerceRate` 在 `getDisableResearch() > 0` 时不区分商业类型，直接返回 `0`；因此 `COMMERCE_FOOD` 的商业收入也为 `0`，并由 `calculateBaseNetFood` 纳入净食物计算（`CvPlayer.cpp:7181-7189,11577-11603`）。
- **推断风险**：禁用研究期间，即使玩家账面存在食物商业 rate，净食物计算中的该收入分量也可能消失。
- **产品意图未知**：禁用研究是否应同时禁用玩家食物商业收入不能由静态接口确定，F006 的食物收入目标保持不变。
- **运行未知**：需在非零 `COMMERCE_FOOD` 条件下切换禁用研究状态，对账 HUD、财务顾问与回合结算；静态证据不构成游戏内复现结论。

## F007 原生信息与反馈闭环

### 功能定义

- 主 HUD 必须显示玩家级食物储备和净变化。
- 选中单位面板必须显示生命、护甲和“近战强度 × 攻击次数”。
- 文明百科单位页必须显示最大生命、护甲、近战强度与次数，以及存在时的远程强度与次数和移动力。
- 近战目标预览必须显示攻击方命中概率、单次伤害、攻击次数、目标生命，以及防守方反击的对应信息。
- 远程单位动作栏必须提供可见的远程目标模式；合法目标可选择，非法目标不能提交动作。
- 战斗日志必须把近战与远程事件以同一字段语义展示给交战双方。
- 财务顾问必须把玩家级食物放在独立于金币收支的可读位置。
- 容量拒绝至少必须以“单位不移动/动作不提交”的一致结果呈现；专用容量数值提示不属于仓库可确认的交互承诺。

### 验收标准

**AC-F007-01 单位信息对账**

- Given 一个拥有近战和远程属性的单位
- When 分别查看选中单位面板、百科页和目标预览
- Then 同名属性与 XML 数值一致，不把远程次数显示成近战次数

**AC-F007-02 战斗对账**

- Given 一次包含命中与落空的战斗
- When 比较目标预览、日志和结算后生命
- Then 日志伤害总和与生命变化一致，日志的骰值与门槛能够解释命中/落空

**AC-F007-03 食物对账**

- Given 玩家食物收入、军事成本和储备均非零
- When 比较 HUD、财务顾问和下一回合储备
- Then `下一储备 = max(0, 原储备 + 收入 - 成本)`；低于 0 的部分按 F006 转换为金币损失
